## 为什么是上下文

一个 Agent 在开始工作前，需要知道任务目标、相关代码、工具说明和已经完成的步骤。这些信息都在争夺有限的上下文窗口。

提示词写得再好，如果模型看不到它需要的那几行代码，结果也不会好。所以真正要设计的，是**模型在每一步能看到什么**。

### 三类信息

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| 稳定信息 | 项目约定、工具说明 | 每次都需要，适合放在开头 |
| 任务信息 | 需求、相关文件 | 随任务变化 |
| 过程信息 | 工具调用结果、报错 | 增长最快，需要压缩 |

## 工具的边界

工具定义本身也是上下文。一个描述清楚的工具，比一段冗长的说明更有用：

```json title="tool.json"
{
  "name": "search_code",
  "description": "在仓库中按关键字搜索代码，返回文件路径和匹配行。",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "要搜索的关键字" }
    },
    "required": ["query"]
  }
}
```

几条经验：

1. 名字和描述要说明**什么时候该用**，而不只是做什么
2. 返回结果要精简，别把整个文件塞回去
3. 出错时返回可以据此行动的信息

:::tip[一个判断标准]
如果一位新同事只看工具描述就知道什么时候该用它，模型大概率也能。
:::

> [!WARNING]
> 工具返回整份大文件，会很快挤占上下文窗口，后面的推理质量随之下降。

## 我的理解

上下文管理和写代码时管理内存很像：放什么、什么时候清理、哪些值得缓存。下一步想试试在长任务里定期让 Agent 自己写进度摘要，看看能不能减少重复劳动。
